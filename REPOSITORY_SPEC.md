# AstraMax Reviewer — Repository Specification

## 1. Purpose

This document defines the initial public repository structure and publishing requirements for **AstraMax Reviewer**, an Agent Skill designed to add an independent second-model review stage to software development workflows.

The repository must be suitable for:

1. Local development and maintenance.
2. Installation directly from GitHub by Agent Skills-compatible tooling.
3. Discovery by SkillsMP and similar Agent Skills indexes.
4. Distribution as a public npm package using SkillPM.
5. Installation through `npx skillpm`.
6. Future evolution without coupling the project to a specific Claude Code or Codex CLI implementation detail.

The repository should remain intentionally small.

This is an **Agent Skill project**, not a Node.js application.

---

# 2. Product concept

## 2.1 Problem

AI coding agents are capable of implementing substantial software changes, but an implementation generated by one model can still contain:

- incorrect assumptions;
- incomplete implementation;
- missed requirements;
- regressions;
- weak tests;
- architectural inconsistencies;
- security problems;
- subtle logic errors;
- unnecessary complexity;
- changes that technically work but contradict the project's design.

Using the same agent to implement and review its own work reduces reviewer independence.

A second strong model provides a different reasoning path and can challenge the implementation before the developer accepts it.

## 2.2 Proposed workflow

AstraMax Reviewer introduces a deliberate separation of responsibilities:

```text
Developer
   |
   v
Claude Code
Primary implementation
   |
   v
Implementation checkpoint
   |
   v
AstraMax Reviewer
   |
   v
OpenAI Codex
GPT-6 Astra
maximum supported reasoning effort
   |
   v
Independent review
   |
   +--> defects
   +--> requirement gaps
   +--> test gaps
   +--> architecture concerns
   +--> security concerns
   +--> unnecessary complexity
   +--> verification evidence
   |
   v
Developer / implementing agent
decides what to change
```

The central idea is not simply:

> "Ask another LLM whether the code is good."

The skill should establish a **repeatable review protocol**.

The reviewing model must actively inspect evidence and attempt to disprove the correctness of the implementation.

# 3. Positioning

AstraMax Reviewer is intended primarily for developers who use:

- Claude Code as an implementation agent; and
- OpenAI Codex with access to GPT-6 Astra as an independent reviewer.

The default reference workflow is:

> Claude implements. Astra reviews.

However, the design should avoid unnecessary coupling.

The underlying principle is:

> Separate implementation and verification across independent model contexts.

Future versions may allow other implementation agents while retaining Astra as the reviewer.

---

# 4. Project philosophy

The project should optimize for:

### Independence

The reviewer should not simply continue the reasoning of the implementing agent.

It should independently inspect the repository, requirements, changes and verification evidence.

### Evidence over opinion

A review finding should preferably be supported by:

- code references;
- diffs;
- test results;
- static analysis;
- repository documentation;
- requirements;
- reproduction steps;
- observable behavior.

### Adversarial verification

The reviewer should actively look for reasons why the implementation may be incorrect.

### Low operational complexity

The skill should remain mostly instructions and reference material.

Avoid creating an application, service, daemon or framework unless there is a demonstrated reason to do so.

### Developer control

The reviewer reports findings.

It should not silently modify the implementation unless the user explicitly requests that behavior.

# 5. Scope of version 0.1

Version `0.1.0` should focus exclusively on the review workflow.

The skill should be capable of reviewing:

- recently implemented features;
- bug fixes;
- refactors;
- repository-wide changes;
- implementation against specifications;
- implementation against tasks or acceptance criteria;
- tests;
- architecture-sensitive changes;
- pre-commit changes;
- pre-PR changes;
- pre-release changes.

The initial version does NOT need to:

- provide a web interface;
- call external APIs directly;
- manage billing;
- manage model credentials;
- replace Claude Code;
- automatically fix every issue it finds;
- orchestrate large multi-agent teams.

Those features may be evaluated later.

# 6. Reviewer responsibilities

The reviewer should examine the implementation across several dimensions.

## Correctness

Determine whether the implementation actually satisfies the requested behavior.

Check:

- requirements;
- acceptance criteria;
- edge cases;
- error handling;
- data transformations;
- state transitions;
- failure paths.

## Regression risk

Look for existing functionality that may have been unintentionally affected.

## Tests

Determine whether tests:

- exist;
- cover relevant behavior;
- cover failure cases;
- genuinely validate the implementation;
- could pass while the implementation remains incorrect.

Run appropriate tests when execution is available.

## Architecture

Check whether the change respects:

- existing project architecture;
- module boundaries;
- dependency direction;
- public contracts;
- existing patterns;
- maintainability expectations.

Avoid criticizing stylistic differences that do not materially affect the project.

## Security

Inspect security-sensitive changes where relevant, including:

- authentication;
- authorization;
- secret handling;
- unsafe input;
- injection risks;
- file access;
- command execution;
- network access;
- dependency changes.

## Data integrity

When relevant, inspect:

- schema changes;
- migrations;
- transaction behavior;
- idempotency;
- serialization;
- data loss risk;
- backward compatibility.

## Complexity

Identify code that is unnecessarily complex relative to the requirement.

Do not recommend abstractions merely for aesthetic reasons.

## Specification compliance

When specification documents exist, treat them as primary review evidence.

Compare implementation against:

- specs;
- plans;
- ADRs;
- issues;
- task documents;
- acceptance criteria;
- project documentation.

# 7. Review workflow

The skill should follow approximately this sequence.

## Phase 1 — Establish review scope

Determine what changed and why.

Inspect relevant sources such as:

```text
git status
git diff
git diff --staged
git log
repository documentation
project specifications
task files
tests
configuration
```

Do not assume that a diff alone contains sufficient context.

## Phase 2 — Understand intended behavior

Identify:

- requested change;
- expected behavior;
- affected components;
- relevant constraints;
- acceptance criteria.

If documentation exists in the repository, read it before evaluating implementation decisions.

## Phase 3 — Inspect implementation

Read the changed code and enough surrounding code to understand its behavior.

Do not review files as isolated fragments when their correctness depends on other modules.

## Phase 4 — Challenge the implementation

Attempt to find cases where the implementation fails.

Ask questions such as:

- What assumption could be false?
- Which input breaks this?
- Which existing behavior could regress?
- Which requirement was implemented only partially?
- Can the test pass while the feature is broken?
- Is failure behavior safe?
- Is there a simpler implementation?
- Does a configuration change create environment-specific failure?
- Does the implementation rely on undocumented behavior?

## Phase 5 — Verify with tools

When appropriate and permitted, use repository tools.

Examples:

```text
test suite
linters
type checker
build
static analysis
existing project validation scripts
targeted reproduction
git inspection
```

Never claim that a test passed unless it was actually executed.

Distinguish clearly between:

```text
verified fact
reasoned concern
hypothesis requiring verification
```

## Phase 6 — Report findings

Produce a concise review organized by severity.

## Phase 7 — Verdict

Finish with one of:

```text
PASS
PASS WITH MINOR FINDINGS
CHANGES RECOMMENDED
CHANGES REQUIRED
UNABLE TO VERIFY
```

The verdict must be justified by the findings.

---

# 8. Finding severity

Use four primary severity levels.

## BLOCKER

The implementation should not be accepted in its current form.

Examples:

- major requirement not implemented;
- data loss;
- serious security vulnerability;
- code does not execute;
- destructive migration;
- critical regression.

## HIGH

Material defect likely to affect production behavior or correctness.

## MEDIUM

Relevant issue that should normally be addressed but may not block the entire change.

## LOW

Minor improvement with limited correctness impact.

Avoid inflating severity.

Stylistic preference alone normally should not become a finding.

---

# 9. Finding format

Each meaningful finding should contain:

```text
Severity:
Location:
Problem:
Evidence:
Impact:
Recommended action:
Verification:
```

Example structure:

```text
HIGH — Authentication bypass on missing tenant identifier

Location:
src/auth/authorization.py:84

Problem:
The authorization path treats a missing tenant identifier as equivalent
to unrestricted access.

Evidence:
...

Impact:
...

Recommended action:
...

Verification:
Add a negative test where...
```

Do not fabricate line numbers or test results.

# 11. Default reviewer behavior

AstraMax Reviewer should be **review-only by default**.

The reviewing agent may:

- inspect files;
- inspect diffs;
- inspect git history;
- execute safe project validation commands;
- run tests;
- run builds;
- perform static analysis;
- explain defects;
- recommend changes.

It should NOT automatically:

- rewrite implementation;
- commit files;
- push branches;
- modify production resources;
- publish releases;
- delete data;

unless explicitly requested by the user.

This separation is intentional.

The reviewer is a reviewer first.

# 12. Astra configuration

The preferred reviewer model is:

```text

```

The preferred reasoning configuration is:

```text
maximum supported reasoning effort
```

At the time of implementation, the repository maintainer should verify the currently supported Codex configuration syntax before hardcoding any invocation command.

The skill should distinguish:

```text
desired reviewer configuration
```

from:

```text

```

If Astra or maximum reasoning effort is unavailable in the user's environment, the skill must say so instead of silently claiming that the intended reviewer configuration was used.

Fallback behavior may be introduced later.

Version 0.1 should prefer transparency over automatic fallback.

# 34. DESIGN.md

Document the key architecture decision:

## Why a second model?

The objective is not model competition.

The objective is **reasoning independence**.

An implementing model has already formed assumptions about:

- requirements;
- architecture;
- interpretation;
- implementation strategy.

A second independent model receives the opportunity to challenge those assumptions.

This is analogous to software engineering practices where authorship and review are separated.

The project should not claim that model diversity automatically produces correctness.

It should state that independent review creates an additional verification opportunity.
